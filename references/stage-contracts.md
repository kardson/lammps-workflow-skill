# Deposition stages and supplied-observation checks

`templates/stage-contract.json` proposes preparation, thermalization, deposition, post-relaxation and sampling roles. These are unconfirmed candidate stages; all scientific values remain null. The project plan is authoritative. Binding a draft to a plan snapshot does not confirm the stage choices or authorize a run.

`tools/stage_contract.py` is a non-launching library. `audit(contract)` checks supported declared intervals, integrator atom-ID overlap, basic temperature/open-system declarations and numerical stop conditions. It reports INVALID, PARTIAL or DECLARATIONS_COMPLETE_NOT_RUNTIME_VALIDATED. It does not parse actual LAMMPS groups/fixes or validate arbitrary selection expressions. Unknown dynamic memberships remain unresolved rather than assumed disjoint.

`schemas/stage-contract.schema.json` validates structure before semantic checks; null-valued drafts remain valid partial records. Schema validation requires the optional jsonschema dependency in requirements-validation.txt. `tools/inspect_stages.py --contract FILE` prints a read-only audit. Add both `--observation OBS.json --stage STAGE_ID` to inspect one supplied observation. Exit 0 means declarations complete or no declared condition triggered, not scientific acceptance; 1 means invalid/partial/unknown/triggered or requested source-link gaps; 2 means input/dependency/usage error. Nonfinite JSON tokens are rejected; missing/nonfinite direct-library measurements remain unknown.

Stages use half-open [start_step,end_step) intervals with explicit timestep_ps and physical_time_origin_ps. Within a constant-step stage, time is origin + (step-start_step)*timestep_ps; resets, changed timesteps and parent-attempt origins need explicit stage boundaries. A final-boundary snapshot does not silently belong to both stages. Static preparation events without a time interval must remain unresolved or use a separate preparation record; no duration is invented.

Record fixed/bath/mobile/incoming roles, actual integrator fixes and memberships, temperature compute/selection, streaming-velocity treatment, dynamic DOF and extra DOF. Changing particle counts require dynamic DOF or explicit alternative evidence. Record reservoir energy/heat-flow definition and units separately from incoming kinetic/potential energy and removal losses. An insertion attempt counter, successful insertion counter and retained particle count are distinct and need explicit origins/source definitions.

Every numerical stop condition declares id, quantity, operator (gt/lt/abs_gt), threshold, unit, reason and source. Missing thresholds remain unknown, not defaults. Open or changing-N stages cannot use a closed-system total-energy-conservation criterion. Thermostatted fixed-N stages also need appropriate heat/work accounting; passing this declaration audit does not establish a physically valid conservation test. Temperature stability alone is never an equilibrium acceptance criterion here.

`inspect_observation(contract,stage_id,observation)` accepts a supplied step, source and quantities {name:{value,unit}}. Missing/nonfinite values, wrong units, incomplete conditions or steps outside the stage report UNVERIFIED. Known threshold exceedance reports CONDITION_TRIGGERED with its reason. No condition triggered is not equilibrium or scientific acceptance. The library sends no signals, changes no parameters/potentials, launches no monitoring loop and performs no training. Runtime enforcement needs a separately reviewed implementation and authorization.

Engine support is declared per stage with its actual profile/scenario/evidence; an arbitrary engine name or old help output is not proof. Reuse version-matched manual and recorded insertion/restart evidence only within its tested bounds. The public template intentionally contains no host paths, production thresholds or default semiconductor parameters.

Optional `--reference-root PROJECT` checks the plan_binding file/id/hash and stage engine_support links. engine_support declares profile_file/profile_sha256, engine_id, model_sha256 (the selected model/parameter identity), evidence_file/evidence_sha256, scenario and required_dimensions. Paths are project-relative, files limited to 4 MiB, and profile records may be standalone or in the existing profiles list. required_dimensions explicitly selects installation/numerical/mpi/deposition/restart/physical_accuracy evidence; every requested dimension needs matching recorded support. A numerical check alone cannot satisfy a requested restart/deposition check. Unsupported/absent empirical or ML evidence remains unknown, not a reason to invent compatibility. Matching files and scenarios do not establish current host readiness or stage physical validity.
